## 1. 为什么“只移动”可以不触发 P9

不靠“应该不会”，而是用门控把破坏性动作从执行器里删掉：

- 只允许 `mkdir` 和 `move` 两种 op；
- 不允许 `delete`、`copy`、`exec`、`robocopy /MIR` 等动作；
- 所有 move 必须 `src`、`dst` 都在 `H:\`，保证同盘；
- `dst` 必须不存在，禁止覆盖；
- 使用 .NET `File.Move` / `Directory.Move`（同卷移动，目标已存在会失败），不用可覆盖的 `Move-Item -Force`；
- 源路径含 reparse point / symlink / junction 一律拒绝；
- 系统目录、回收站、应用托管目录、H 根本身一律拒绝；
- 任一前置条件失败即停止，不做“继续下一个看看”。

在这个设计下，移动是**同盘可逆重命名**，不产生“复制后删除源”的跨盘语义。只要没有删除分支，P9 类不可逆操作不会被执行。

## 2. 收纳结构（建议）

在 H 盘根下新建唯一收纳根：

```text
H:\_整理收纳\
├─ 10_工作项目\
├─ 20_专业资料\
├─ 30_文档表格\
├─ 40_图片\
├─ 50_视频音频\
├─ 60_软件与镜像\
├─ 70_压缩归档\
├─ 80_旧备份\
└─ 90_待确认\
```

规则：

- 只允许把东西移进 `H:\_整理收纳\...`；不改现有目录名，不做“重命名式整理”。
- 目标路径尽量保留原目录名，例如：
  - `H:\某项目\` → `H:\_整理收纳\10_工作项目\某项目\`
  - `H:\某根文件.xlsx` → `H:\_整理收纳\30_文档表格\根目录文件\某根文件.xlsx`
- 首轮不建大而全的分类；`90_待确认` 用来放“边界不清但用户已同意从原位置挪走”的对象。
- 不自动改文件名，不自动去重，不自动合并同名目录；冲突就停并交人工决定。

## 4. Windows 侧整理流程

### P0 只读基线（不写 H）

1. 记录 H 盘卷信息、PowerShell 版本、长路径开关、权限；
2. 生成顶级清单：名称、类型、大小、修改时间、属性、是否 reparse；
3. 统计顶级目录数量和空间，不递归深入未知大目录；
4. 把基线写到 Windows 本地工作目录，例如：
   `C:\Users\Administrator\h-cleanup\<run-id>\inventory\`。

### P1 盘点与候选分类

- 先只盘点**用户指定的第一轮范围**；不要默认全盘。
- 每个对象给一个 `item_id`，并分类：
  - `KEEP_IN_PLACE`：不动；
  - `HOLD`：信息不足/应用托管/系统；
  - `MOVE_PROJECT`：项目目录；
  - `MOVE_DOC`：文档表格；
  - `MOVE_IMAGE`：图片；
  - `MOVE_VIDEO`：视频；
  - `MOVE_INSTALLER`：安装包/镜像；
  - `MOVE_ARCHIVE`：压缩归档；
  - `MOVE_REVIEW`：待确认。
- 分类结果必须 100% 覆盖第一轮范围内对象；不能只挑大的。

### P2 生成 move 计划（只写本地账本）

每个动作一行 JSON，至少包含：

```json
{
  "id": "ACT-0001",
  "op": "move",
  "src": "H:\\某目录\\某文件",
  "dst": "H:\\_整理收纳\\30_文档表格\\某目录\\某文件",
  "item_type": "file",
  "intent": "用户确认的文档收纳",
  "item_count": 1,
  "size_bytes": 12345,
  "last_write": "2026-10-18T12:00:00",
  "dry_run": "planned"
}
```

约束：

- 一行一个对象/一个目录，不允许多源多目标；
- `src` 必须是完整绝对 Windows 路径，`dst` 必须已确定且不存在；
- 对目录 move，先把整个目录看作一个对象，不做目录内逐文件拆散；
- 任何不确定项不生成可执行 action，只进 `90_待确认` 清单。

### P3 dry-run 门控

每条 move 在真正执行前要全部检查：

1. `src` 和 `dst` 都以 `H:\` 开头；
2. `src` 存在，`dst` 不存在；
3. `dst` 父目录在 `H:\_整理收纳\` 内或计划内；
4. `src` 不是 H 根、系统目录、应用托管目录；
5. `src` 及其父链无 reparse point；
6. 路径长度不超安全阈值（PowerShell 5.1 + 长路径关闭，建议 ≤240）；
7. 不是通配符、保留设备名、ADS 路径；
8. 没有跨盘、复制、删除、覆盖、脚本执行。

全部通过 = `PASS`；任一失败 = `FAIL`，进入独立 SAFETY 逐条审核。审核记录一条只能对应一个 action。

### P4 执行（一次一个）

实现上使用 .NET 同盘移动：

```text
文件:      [System.IO.File]::Move($src, $dst)
目录:      [System.IO.Directory]::Move($src, $dst)
```

不使用 `Move-Item -Force`，也不使用 `robocopy /MOVE`。执行前后各自校验：

- 成功后：`src` 不存在，`dst` 存在；
- 文件：目标大小与源记录一致；
- 目录：目标目录存在，源目录不存在；
- 失败：立刻停，不继续下一 action，记录错误码/异常信息；
- 不在失败后自动重试，必须重新生成新 action 并重新门控。

### P5 验证与回滚

- 每批结束后重新生成 H 顶级清单；
- 对照变化：只允许计划内的路径变化；
- 生成 `rollback.jsonl`：`dst → src` 的反向 move 列表；
- 回滚同样走门控，且目标位置必须为空；
- 回滚失败也停止，不覆盖任何现有对象。

### P6 人工确认与下一批

- 第一批只挑 10–20 个低风险对象试跑；
- 用户确认第一批无误后，再扩大分类范围；
- 第二批才考虑项目目录/大型目录；
- 应用托管目录永远不在“自动 move”范围。

## 5. 首轮试点建议（低风险）

优先从以下类型中挑 10–20 个对象，而不是一上来搬项目目录：

1. 根目录下明确的安装包、镜像、压缩归档 → `60_软件与镜像` / `70_压缩归档`；
2. 根目录下明确的文档/表格/PPT 单文件 → `30_文档表格`；
3. 已确认不再使用、且不是应用托管的旧目录 → 对应分类；
4. 任何不确定的根级对象只进 `90_待确认` 清单，不移动。

不建议首轮：

- `OneDrive`、`FileHistory`、`SteamLibrary`、`Android`、微信/QQ/WPS/Baidu 等应用目录；
- 当前项目、Petrel/专业软件工程目录；
- 任何带 junction/reparse 的目录；
- 任何嵌套层级很深或长路径的对象。

## 6. 安全门控与独立安全员（Windows 版）

现有 `scripts/hdrive_gate.py` 是 POSIX 路径门控，不能直接用于 `H:\`。Windows 侧需要新增一个极简的 `hdrive_move_gate.ps1`，只实现：

- `init`：确定根、收纳根、安全审核员、人工批准人；
- `propose`：登记 move/mkdir action，计算 digest；
- `gate`：跑上述 8 条检查；
- `review`：SAFETY 逐条 approve/reject（一次一个 action）；
- `run`：只执行已放行 move/mkdir；
- `status`：输出 PASS/FAIL/pending/executed 数字。

角色规则不变：

- 提出 action 的 TDO 不能自己审；
- SAFETY 必须是独立会话，不执行；
- 每条 FAIL 必须有且只有一条审核记录；
- 禁止批量审核、代签、改 action 后沿用旧 digest；
- 执行前重新校验 digest 和前置条件；
- 未审核 FAIL 或任一门控不通过 = 不执行。

## 7. 日志位置与隐私

- 原始清单/账本建议先放 Windows 本地：
  `C:\Users\Administrator\h-cleanup\<run-id>\`；
- 脱敏后的摘要再同步到工作流 `runs/<run-id>/reports/windows/`；
- 不在 H 盘写入“日志文件”作为整理副作用，除非用户明确同意；
- 不把完整文件名列表、个人路径、文件内容提交到公开仓库或 push。

## 8. 需要用户确认的 6 件事

1. 收纳根是否用 `H:\_整理收纳`，分类名是否按本文默认；
2. 首轮试点范围：允许我挑 10–20 个低风险对象，还是你指定目录；
3. 项目目录/专业软件工程目录是否首轮不动（建议不动）；
4. 应用托管目录（OneDrive/Steam/微信/WPS/Baidu/Android 等）是否确认只登记不动；
5. 独立 SAFETY 与人工批准人的身份；
6. P9 的准确定义；若 P9 = 不可逆删除/破坏性操作，本 move-only 方案从机制上不会触发。

## 9. 下一步

用户确认第 8 节后，按以下顺序推进：

1. 新增 Windows 版 move-only 门控脚本与测试（只在临时目录测试，不碰 H）；
2. 生成第一批只读候选清单给用户勾选；
3. 用户批准试点对象；
4. 执行 10–20 个 move，验证、留回滚；
5. 用户复核后再扩大。

## 11. 两轮工作流安排

### Round 1：冻结 + 盘点 + 高置信整目录归位

1. 生成 H 盘顶级只读清单和关键目录第一层清单；
2. 写入 protected manifest：A 组全部标记 `KEEP_TOP`，根 Excel/PPT 标记 `KEEP_ROOT`；
3. 为 B/C/D/E/F 组中高置信对象生成整目录/单文件 move action；
4. dry-run 检查：路径、目标不存在、父目录存在、无 reparse、无长路径、H 盘内；
5. 独立 SAFETY 审核每个 FAIL action；
6. 一次一个执行 move，记录每一条的 source/dest/大小/时间；
7. 结束后做前后清单对账；
8. 不处理 G 组混合区，下一轮做。

Round 1 的产出：

- `reports/r1-top-level-inventory.jsonl`
- `reports/r1-protected-manifest.md`
- `reports/r1-move-ledger.csv`
- `reports/r1-verification.md`

### Round 2：拍扁 + 按树聚合 + 混合区收尾

1. 对 D 组媒体做文件级扁平/浅树聚合；
2. 对 C 组冷备份做内部树整理（只 move，不删除）；
3. 对 G 组混合区做逐文件分类和移动；
4. 对 B 组工作资料中已确认无路径依赖的目录，按用户规则做浅树聚合；
5. A 组 protected paths 永远不进入 action 队列；
6. 全量核对 move ledger：每个旧路径都有唯一新路径，目标无丢文件；
7. 产出 hold list，只保留确实需要用户决定的少量对象。

Round 2 的产出：

- `reports/r2-file-ledger.csv`（每个文件一行：旧路径 → 新路径）
- `reports/r2-final-layout.md`
- `reports/r2-hold-list.md`
- `reports/r2-verification.md`

### “干净”的判定

- A 组路径和内容完全未变；
- 根 Excel/PPT 完全未动；
- 每个被移动文件都有旧路径、新路径、大小、时间、批次、状态；
- 无覆盖、无删除、无跨盘复制、无 reparse 目标；
- G 组混合区至少有明确去向或进入 `90_待确认`；
- 目标目录树可读、可搜索、可按来源追溯；
- 若仍有 `90_待确认`，运行以“已知遗留清单”结束，而不是假装清空。

## 12. 关于“破坏性整理”和 P9 的口径

- 本方案把“破坏性整理”定义为：**打散旧文件夹层级、拍扁、按树聚合、移动文件位置**；
- 不把“永久删除文件”纳入本方案。因为用户同时要求“每个文件的去向可追溯”；删除会改变这个前提；
- 如果确认要做永久删除，必须另加 `purge` 红动作：独立 SAFETY 审核 + 独立人工批准 + 删除清单/hash + P9 硬阻断，不能混在 move 动作里；
- 因此在当前 move-only 方案里，P9 类不可逆删除路径不存在；文件夹拍扁只是路径重组，仍可通过 ledger + 反向 move 回滚。
